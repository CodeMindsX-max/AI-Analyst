# AnalystAI — Security Architecture & Production Policy

This document defines the security architecture, threat model, mitigation strategies, and production checklist for **AnalystAI**.

---

## 1. Threat Model & Mitigation Overview

As an AI-assisted business data analysis platform converting natural-language business inquiries into SQL queries, AnalystAI enforces layered security boundaries across authentication, query validation, analytical execution, file processing, and environment secrets.

```
+-----------------------------------------------------------------------------------+
|                               Security Boundaries                                 |
+-----------------------------------------------------------------------------------+
|  1. Ingress & Auth:       JWT HS256 Token Verification + AppShell Route Guards    |
|  2. Credential Storage:   Pure Bcrypt (12 rounds) + Legacy Migration Flow         |
|  3. SQL Safety Layer:     AST Validation + C-Level SQLite Authorizer              |
|  4. Connector Isolation:  Analytical DB read-only separation, source validation   |
|  5. RAG / File Security:  MIME check, 25MB limit, path traversal sanitization     |
|  6. Secret Management:    Environment variables via Pydantic; redacting repr      |
+-----------------------------------------------------------------------------------+
```

## 2. Authentication & Credential Storage

### 2.1 Password Hashing Architecture
- **Primary Algorithm**: Pure `bcrypt` hashing with individual salt generation (`bcrypt.gensalt(rounds=12)`).
- **Password Length Boundary**: Passwords are truncated to 72 bytes before hashing to respect bcrypt's hard computational boundary and prevent `ValueError`.
- **Legacy Migration & Auto-Upgrade**:
  - Legacy users created with salted SHA-256 (`salt$sha256_hash`) are verified against the legacy algorithm.
  - Upon successful verification, the password hash is automatically upgraded to bcrypt via `needs_rehash()` and persisted to the database.
- **Verification Function**: Uses constant-time comparison `bcrypt.checkpw()` to mitigate timing side-channel attacks.

### 2.2 JWT Token Security
- **Algorithm**: Enforced `HS256`. The verification layer explicitly specifies `algorithms=["HS256"]` to prevent algorithm substitution attacks (e.g. `none` algorithm attacks).
- **Token Claims**: Contains only minimal non-sensitive identity claims: `sub` (user email), `exp` (expiration), `iat` (issued at). Never includes passwords, database credentials, or secret keys.
- **Expiration Policy**: Configurable via `ACCESS_TOKEN_EXPIRE_MINUTES` (default: 480 minutes / 8 hours in development, recommend 30-60 minutes in production).
- **Secret Key Enforcement**: In production (`APP_ENV=production`), `Settings` rejects default, weak, or short secrets (`SECRET_KEY` must be at least 32 characters long).

### 2.3 Frontend Route Protection
- `AppShell.tsx` inspects authentication state before rendering any application layout or feature component.
- If `/api/v1/auth/me` returns 401 or network failure, the application resets authentication state and immediately redirects to `/login`.
- **Zero Fake Admin Fallbacks**: Fallback demo admin logic in `AppProviders.tsx` has been eliminated. Unauthenticated sessions are never granted access to protected views.

## 3. SQL Safety & Analytical Query Boundaries

AnalystAI features dual-layer SQL security to ensure queries generated by Text-to-SQL or entered in the SQL Workspace cannot modify or exfiltrate data maliciously:

### Layer 1: Abstract Syntax Tree (AST) Validation
Before any query reaches an execution engine, `backend/app/services/sql_safety_service.py` parses the statement using `sqlglot`:
- Rejects any statement that is not a `SELECT` statement.
- Blocks destructive commands: `DROP`, `ALTER`, `TRUNCATE`, `INSERT`, `UPDATE`, `DELETE`, `ATTACH`, `DETACH`, `CREATE`, `REPLACE`.
- Rejects multiple statements (semicolon separation) to prevent stacked SQL injection.

### Layer 2: C-Level SQLite Authorizer Callback
For local analytical SQLite queries:
- Configures `sqlite3.set_authorizer(sqlite_read_only_authorizer)` on the connection object.
- Rejects `SQLITE_INSERT`, `SQLITE_UPDATE`, `SQLITE_DELETE`, `SQLITE_ATTACH`, `SQLITE_DETACH`, and schema alteration actions at the SQLite engine level before execution touches disk.

### Critical SQL Safety Limitation & External Database Policy
> [!WARNING]
> AST parsing and regex checks are **not an infallible security boundary** across diverse database dialects (PostgreSQL, Oracle, SQL Server, MySQL).
> 
> **Production Requirement for External Databases**:
> - AnalystAI must **never** connect to customer databases using administrative (`sa`, `postgres`, `root`) credentials.
> - Customer database credentials configured in AnalystAI must belong to a dedicated **read-only database role** configured with `CONNECT` and `SELECT` privileges only on target analytical tables.
> - Always enforce query execution timeouts (capped at 30 seconds) and maximum result row limits (capped at 1,000 rows).

## 4. File Upload & RAG Boundary Protection

The Knowledge Base allows uploading reference documents (`.txt`, `.csv`, `.xlsx`, `.pdf`) for contextual retrieval.

### 4.1 Path Traversal Mitigation
- Uploaded files are assigned UUID-based filenames and stored in `data/uploads/`, completely isolated from public frontend static assets.
- Filenames undergo strict boundary validation:
  ```python
  clean_filename = os.path.basename(file.filename)
  file_path = os.path.abspath(os.path.join(upload_dir, f"{doc_id}_{clean_filename}"))
  if not file_path.startswith(os.path.abspath(upload_dir)):
      raise HTTPException(status_code=400, detail="Invalid file path trajectory")
  ```

### 4.2 File Size & Content Validation
- Maximum file size: **25 MB** (`MAX_FILE_SIZE = 25 * 1024 * 1024`).
- Unsupported file formats (e.g. `.docx`, `.exe`, `.bat`, `.sh`) are rejected with explicit HTTP 400 validation errors.
- Never execute macros, scripts, or active content contained within uploaded files.

## 5. Secret Management & Credential Rotation

### 5.1 Redacting Configuration Logging
- `backend/app/core/config.py` overrides `__repr__` and `__str__` to mask `SECRET_KEY`, `DATABASE_URL`, and any field containing `key`, `secret`, `token`, or `password`.
- Connection URLs logged during health checks or startup display only the driver and hostname, masking credentials (e.g. `postgresql+psycopg://***:***@db.host.supabase.com:6543/postgres`).

### 5.2 Credential Rotation Procedure
If credentials or `.env` files are accidentally exposed:
1. **Supabase Database Password**:
   - Navigate to Supabase Dashboard -> **Project Settings** -> **Database**.
   - Click **Reset database password** and generate a strong 32+ character random password.
   - Update `backend/.env` with the new password (URL-encoded).
2. **Application Secret Key**:
   - Generate a new random 64-character hex key:
     ```powershell
     python -c "import secrets; print(secrets.token_hex(32))"
     ```
   - Update `SECRET_KEY` in `backend/.env`. Note: this invalidates existing user sessions, requiring users to log in again.
3. **External Customer Database Credentials**:
   - Rotate database user passwords on the customer database server.
   - Re-enter connection strings in AnalystAI Data Sources settings.

## 6. Audit Trail & Accountability

AnalystAI logs security-relevant actions to the immutable `audit_events` table in `ApplicationBase`:
- User authentication events (successful login, failed attempts, logout).
- SQL workspace query executions (with actor ID, query text, execution duration, and row counts).
- Data source registrations and configuration changes.
- Team member invitations and role modifications.
- Audit logs cannot be updated or deleted through standard application API endpoints.

## 7. Production Deployment Security Checklist

Before deploying AnalystAI to a staging or production environment:

- [ ] **Environment Mode**: Set `APP_ENV=production` and `DEBUG=false` in `backend/.env`.
- [ ] **Secret Key**: Set `SECRET_KEY` to a unique, randomly generated string of at least 32 characters.
- [ ] **PostgreSQL Application DB**: Use a production-grade PostgreSQL database with SSL enabled (`sslmode=require`).
- [ ] **CORS Policy**: Restrict `CORS_ORIGINS` to the exact production domain(s) of the frontend (e.g., `https://analystai.yourcompany.com`). Do not use wildcard `*`.
- [ ] **No Default Credentials**: Ensure demo seed accounts (`demo@analystai.local`) are changed or disabled in production.
- [ ] **Customer DB Roles**: Verify customer database connections use dedicated read-only database credentials with no DDL or DML privileges.
- [ ] **Reverse Proxy SSL**: Deploy FastAPI behind an SSL-terminating reverse proxy (Nginx, Traefik, AWS ALB, or Cloudflare) with HTTP Strict Transport Security (HSTS) enabled.
- [ ] **Database Backups**: Schedule automated daily backups and point-in-time recovery for the application PostgreSQL database.
